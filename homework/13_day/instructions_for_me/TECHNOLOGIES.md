## 📝 logging — почему не print

`print` пишет в stdout всё подряд, без уровня важности, без времени и без
указания, откуда сообщение. `logging` из стандартной библиотеки даёт всё
это бесплатно.

### Настройка — одна строка на приложение

```python
logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(name)s: %(message)s")
```

Настраивается **корневой логгер**: сообщения из всех модулей всплывают к
нему и печатаются одним форматом. Отдельный модуль под конфигурацию не
нужен — настройка одна и живёт там, где стартует приложение.

Важно, что вызов стоит **до первого лог-сообщения**: до
`dataset = ChurnDataset()`. Повторные вызовы `basicConfig` молча
игнорируются, поэтому «настроить позже» не получится — потеряются логи
старта.

### Логгер на модуль

```python
logger = logging.getLogger(__name__)   # имя логгера = имя модуля
```

Отсюда в выводе видно источник:

```
2026-08-06 00:39:11,487 INFO dataset: датасет загружен: 2000 строк
2026-08-06 00:39:23,884 INFO main: предсказание для 1 клиентов
2026-08-06 00:39:23,895 WARNING errors: ошибка 404: Not Found
```

### Уровни: не всё одинаково важно

| Уровень | Когда | У нас |
|---|---|---|
| `INFO` | штатное событие | загрузка датасета, обучение, предсказание |
| `WARNING` | что-то пошло не так, но сервис здоров | ошибки клиента 4xx |
| `ERROR` | сломались мы | необработанное исключение (500) |

Уровень — это фильтр: `level=logging.INFO` показывает INFO и выше, а в
проде обычно ставят WARNING, чтобы не тонуть в шуме. Именно поэтому важно
раскладывать события по уровням правильно: 404 от опечатки клиента — не
авария и не должна будить дежурного.

### `logger.exception` — трассировка в лог, но не клиенту

```python
@app.exception_handler(Exception)
def handle_internal_error(request, exc):
    logger.exception("необработанная ошибка")
    return error_response(500, "internal_error", "внутренняя ошибка сервиса")
```

`logger.exception()` = `logger.error()` + автоматическая трассировка
текущего исключения. Получается ровно то, что нужно: разработчик видит,
где сломалось, а наружу уходит аккуратный JSON дня 10 без путей к файлам и
версий библиотек.

### Ленивое форматирование

```python
logger.info("датасет загружен: %s строк", len(self.df))   # так
logger.info(f"датасет загружен: {len(self.df)} строк")     # не так
```

В первом случае строка собирается **только если сообщение действительно
будет напечатано**. При `level=WARNING` вызов INFO не стоит почти ничего.
С f-строкой форматирование происходит всегда — даже когда результат
выбрасывается.

## 💊 GET /health — эндпоинт для машин

```python
@app.get("/health")
def health():
    return {
        "status": "ok",
        "model_available": model_state is not None,
        "dataset_loaded": not dataset.df.empty,
    }
```

Health-check — стандартный приём эксплуатации: по нему Docker, Kubernetes
или балансировщик решают, отправлять ли на сервис трафик и не нужно ли
его перезапустить. Отвечать он должен быстро и без тяжёлой работы.

Чем он отличается от `/model/status` дня 6: `/health` — **технический**
(«я живой, данные на месте, модель загружена?»), `/model/status` —
**прикладной** («какая модель, когда обучена, какие метрики»). У них разные
потребители: первый читают машины, второй — человек.

## 🐳 Docker: образ, слои, контейнер

Docker решает проблему «у меня работает»: в образ кладётся не только код,
но и Python нужной версии, библиотеки и данные.

- **Образ (image)** — неизменяемый слепок файловой системы, собирается по
  `Dockerfile`.
- **Контейнер (container)** — запущенный экземпляр образа. Удалили
  контейнер — исчезло всё, что он записал внутрь себя.

### Разбор нашего Dockerfile

```dockerfile
FROM python:3.11-slim                      # базовый образ: Python без лишнего
WORKDIR /app                               # рабочая папка внутри образа

COPY homework/requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY data/churn_dataset.csv data/churn_dataset.csv
COPY homework/13_day/*.py homework/13_day/

WORKDIR /app/homework/13_day
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**Слои и кеш.** Каждая инструкция создаёт слой. При пересборке Docker
переиспользует слои, входные данные которых не изменились. Поэтому
зависимости копируются и ставятся **до** кода: правка `main.py` не
заставляет заново скачивать pandas и scikit-learn — пересборка занимает
секунды вместо минут. Поменяй порядок — и каждая правка будет стоить полной
переустановки.

**`--no-cache-dir`** — не хранить скачанные пакеты внутри образа: они уже
установлены, а вес образа это уменьшает.

**Структура путей повторяет проект.** `dataset.py` ищет CSV как
`Path(__file__).resolve().parents[2] / "data" / "churn_dataset.csv"`.
Разложив файлы в образе так же, как в репозитории (`/app/homework/13_day/`
и `/app/data/`), мы получили рабочий путь `/app/data/churn_dataset.csv`
**без единой правки кода**. Положи `main.py` прямо в `/app` — и `parents[2]`
упрётся в корень файловой системы и выбросит `IndexError` ещё до старта
сервера. Альтернатива (переменная окружения с путём) потребовала бы
ветвления в коде — нам не понадобилась.

**`--host 0.0.0.0`** — самая частая ошибка новичка. По умолчанию uvicorn
слушает `127.0.0.1`, а внутри контейнера это его собственный петлевой
интерфейс: проброс порта работает, но соединение обрывается.
`0.0.0.0` = «слушать на всех интерфейсах».

**`CMD` в форме списка** (exec form) запускает uvicorn напрямую, без
промежуточного шелла — сигнал `docker stop` доходит до процесса, и он
завершается корректно.

### Build-контекст и `.dockerignore`

```bash
docker build -f homework/13_day/Dockerfile -t churn-day13 .
```

Точка в конце — **build-контекст**: папка, которую демон Docker получает
целиком перед сборкой. `COPY` умеет брать файлы только из контекста,
поэтому собираем из корня репозитория (нужны и `data/`, и
`homework/requirements.txt`), а `Dockerfile` указываем через `-f`. Собирать
из папки дня нельзя: `..` в `COPY` запрещён.

Раз контекст — весь репозиторий, в него попал бы и `.venv/` на сотни
мегабайт. От этого спасает `.dockerignore` (лежит в корне): он исключает
`.venv/`, `.git/`, `__pycache__/`, `*.joblib`, `homework_tasks/`. Работает
как `.gitignore`, но для сборки.

### Запуск и наблюдение

```bash
docker run --rm -d -p 8013:8000 --name churn churn-day13
```

- `-p 8013:8000` — слева порт **хоста**, справа порт **внутри контейнера**;
- `-d` — в фоне, `--rm` — удалить контейнер после остановки;
- `--name` — чтобы обращаться по имени, а не по хешу.

```bash
docker logs churn
```

Логи контейнера — это его stdout: искать файл внутри не нужно, `logging`
пишет в поток, а Docker его сохраняет. Отсюда правило контейнерных
приложений: **логировать в stdout, а не в файлы** — сбором и ротацией
занимается инфраструктура.

**Состояние не переживает контейнер.** Модель, обученная внутри, лежит в
файловой системе контейнера и исчезает вместе с ним. В реальном проекте
артефакты выносят на том (`-v`) или в объектное хранилище — для учебного
образа это лишнее, но помнить полезно.

## 📦 Итог: что нового по сравнению с днём 12

| Технология / приём | Зачем |
|--------------------|-------|
| **`logging.basicConfig`** | единая настройка логов для всего приложения |
| **`getLogger(__name__)`** | в логе видно, из какого модуля сообщение |
| **Уровни INFO / WARNING / ERROR** | отделить штатные события от аварий |
| **`logger.exception`** | трассировка в лог, клиенту — чистый JSON |
| **Ленивое форматирование `%s`** | не тратить время на скрытые сообщения |
| **`GET /health`** | машинная проверка живости сервиса |
| **Dockerfile, слои, кеш** | воспроизводимая сборка, быстрые пересборки |
| **Build-контекст + `.dockerignore`** | в образ попадает только нужное |
| **`--host 0.0.0.0`, `-p`** | сервис доступен снаружи контейнера |
| **Логи в stdout + `docker logs`** | наблюдаемость по-контейнерному |
