## 🎲 predict_proba — вероятности вместо «да/нет»

У классификаторов sklearn два метода предсказания:
- **`predict(X)`** → готовый класс (0 или 1) — решение по порогу 0.5;
- **`predict_proba(X)`** → вероятности каждого класса, строка на объект:

```python
pipeline.predict_proba(X)
# array([[0.9644, 0.0356],     клиент 1: P(останется), P(уйдёт)
#        [0.1091, 0.8909]])    клиент 2
```

Вероятность полезнее голого класса: «уйдёт с вероятностью 0.89» и «уйдёт с
вероятностью 0.51» — оба класс 1, но бизнес-решения разные (кого удерживать
в первую очередь). Поэтому API отдаёт и то и другое.

---

## 🧭 classes_ — не угадываем порядок колонок

Колонки в `predict_proba` идут в порядке атрибута **`classes_`** обученной
модели, а не «по определению 0 потом 1»:

```python
pipeline.classes_          # array([0, 1])
# сопоставляем явно:
{str(int(cls)): float(p) for cls, p in zip(pipeline.classes_, proba_row)}
```

Привычка сопоставлять через `classes_` спасает, когда классы — строки,
их больше двух или порядок неожиданный.

## 📋 PredictionResponseChurn — модель ответа

День 2 дал модель **входа** (`FeatureVectorChurn` валидирует запрос). Теперь
появляется модель **выхода**:

```python
class PredictionResponseChurn(BaseModel):
    prediction: int                    # 0 — останется, 1 — уйдёт
    probabilities: dict[str, float]    # {"0": 0.9644, "1": 0.0356}
```

Зачем оформлять ответ моделью, а не «каким-то dict»:
- **контракт**: клиент точно знает форму ответа;
- **схема в /docs**: Swagger показывает структуру ответа автоматически;
- **валидация на выходе**: перепутали тип — сервис сам поймает.

Ключи `probabilities` — строки, потому что в JSON ключи объекта всегда
строки: честнее сразу объявить `dict[str, float]`.

## 🔀 Union-тип: один объект ИЛИ список

Задание требует принимать и одного клиента, и пачку. В Python это
**union-тип** `X | Y`, и FastAPI понимает его прямо в сигнатуре:

```python
@app.post("/predict")
def predict(features: FeatureVectorChurn | list[FeatureVectorChurn]):
    is_single = isinstance(features, FeatureVectorChurn)
    batch = [features] if is_single else features
    responses = predict_churn(pipeline, batch)
    return responses[0] if is_single else responses
```

FastAPI пробует варианты по очереди: пришёл JSON-объект → распарсит как
`FeatureVectorChurn`, пришёл JSON-массив → как список. Внутри удобно
привести всё к списку (модель всё равно предсказывает батчами), а на выходе
вернуть ту же форму, что была на входе.

## 🐼 Из Pydantic-объектов в DataFrame

Pipeline обучался на DataFrame — на предсказании вход должен выглядеть так
же: те же колонки, те же типы.

```python
X = pd.DataFrame(
    [f.model_dump() for f in features],   # Pydantic-объект -> dict
    columns=FEATURE_COLUMNS,              # тот же набор и порядок, что при обучении
)
```

- **`model_dump()`** — стандартный способ Pydantic v2 превратить объект в
  словарь (в v1 назывался `.dict()`);
- **`columns=FEATURE_COLUMNS`** — явный порядок колонок. ColumnTransformer
  выбирает колонки по именам, так что формально порядок не критичен, но
  явная фиксация — страховка от расхождений train/predict (день 9 сделает
  это требованием).

## 📖 Пример запроса в /docs — json_schema_extra

Чтобы Swagger подставлял в форму `POST /predict` осмысленный пример, а не
нули, к модели входа добавляется пример:

```python
class FeatureVectorChurn(BaseModel):
    model_config = ConfigDict(json_schema_extra={"example": {
        "monthly_fee": 9.99, "usage_hours": 30, ...
    }})
```

Пример попадает в OpenAPI-схему → `/docs` показывает его в теле запроса.
Это документация, которая живёт рядом с кодом и не устаревает отдельно
от него.

## ⚠️ Ошибка «модель не обучена»

Предсказание без модели — ожидаемая ситуация (свежий запуск, файл удалён),
а не исключение в недрах sklearn. Проверяем состояние явно:

```python
if model_state is None:
    raise HTTPException(status_code=400,
                        detail="модель ещё не обучена — вызовите POST /model/train")
```

Клиент получает понятный JSON и знает, что делать. Систематизация ошибок
всего сервиса — тема дня 10.
