# 🧰 Новые технологии дня 12 — pytest, фикстуры и TestClient

День 12 не добавляет сервису ни одной новой возможности — он добавляет
**уверенность**. Раньше проверка изменений выглядела как «запустить
uvicorn и постучать curl'ом»: долго, вручную и легко забыть половину
сценариев. Теперь это одна команда `pytest`.

---

## 🧪 pytest: тест — это обычная функция

```python
def test_unknown_model_type():
    with pytest.raises(ValueError):
        build_model("нет такой", {})
```

Никаких классов и наследования (в отличие от `unittest`): pytest сам
находит файлы `test_*.py` и функции `test_*`, а для проверок использует
обычный `assert` — при падении он показывает реальные значения:

```
FAILED tests/test_model.py::test_train_returns_metrics - assert 0.6738 > 0.75
```

Настройка — файл `pytest.ini`:

```ini
[pytest]
testpaths = tests
```

Он же помечает корень проекта для pytest. Импорты вида `import main`
работают потому, что `conftest.py` лежит в папке дня, и pytest добавляет
эту папку в `sys.path`.

## 🧩 Фикстуры — подготовка данных для теста

Фикстура — функция с декоратором `@pytest.fixture`; тест «просит» её,
указав имя в аргументах:

```python
@pytest.fixture
def synthetic_df():
    ...

def test_split_train_test_shapes(synthetic_df):   # ← pytest сам подставит
    ...
```

Это **инъекция зависимостей**: тест не создаёт данные сам и не знает, как
они устроены. Фикстура вызывается заново для каждого теста, поэтому
изменения в одном тесте не видны другому.

Встроенные фикстуры, которые мы используем:
- **`tmp_path`** — уникальный временный каталог на каждый тест, pytest сам
  его удалит;
- **`monkeypatch`** — временная подмена атрибутов/переменных окружения с
  автоматическим откатом после теста.

## 🎲 Синтетические данные вместо реальных

Задание требует повторяемости, поэтому юнит-тесты работают не на
`churn_dataset.csv`, а на сгенерированном датасете:

```python
rng = np.random.default_rng(42)     # фиксированный seed → одни и те же числа
churn = (rng.random(n) < 0.2).astype(int)
"usage_hours": (rng.normal(30, 8, n) - churn * 10).round(2),   # у ушедших активность ниже
```

Три причины так делать:
1. **Скорость** — 200 строк вместо 2000;
2. **Независимость** — тест не сломается, если в CSV поменяются данные;
3. **Контроль** — мы сами закладываем сигнал (ушедшие клиенты меньше
   пользуются сервисом и чаще не платят), поэтому можем требовать от
   модели осмысленного качества: `assert metrics["roc_auc"] > 0.75`.

Последнее — не придирка. Если посчитать `roc_auc` по меткам вместо
вероятностей (ловушка дня 11), на этих данных получится ≈ 0.67, и тест
падает. Проверка диапазона `0 ≤ roc_auc ≤ 1` такую ошибку пропустила бы.

## 🌐 TestClient — HTTP-запросы без запущенного сервера

```python
from fastapi.testclient import TestClient

client = TestClient(main.app)
response = client.post("/predict", json=CUSTOMER)
assert response.status_code == 409
```

`TestClient` вызывает приложение напрямую через ASGI-интерфейс — сети,
портов и uvicorn нет вовсе. Отсюда скорость (весь набор ≈ 0.2 с) и
отсутствие «занят порт 8000». При этом проходит **весь** реальный путь
запроса: маршрутизация, валидация Pydantic, наши обработчики ошибок,
сериализация ответа. Поэтому такой тест ловит те же ошибки, что и curl.

API у него как у `requests`: `client.get(...)`, `client.post(..., json=...)`,
`params={...}`, `response.json()`.

## 🧷 Изоляция: главная сложность дня

`main.py` выполняет работу **на импорте**:

```python
dataset = ChurnDataset()                 # читает CSV
model_state: dict | None = load_churn_model()   # читает models/churn_model.joblib
```

Из этого следуют две проблемы, и обе решаются в фикстуре `client`.

### Проблема 1: тесты пишут в папку проекта

Обучение через `/model/train` сохранило бы модель и журнал в
`homework/12_day/models/`. Тесты, оставляющие файлы, — плохой тон: следующий
прогон стартует уже не с чистого листа.

```python
monkeypatch.setattr(storage, "MODEL_PATH", tmp_path / "churn_model.joblib")
monkeypatch.setattr(history, "HISTORY_PATH", tmp_path / "training_history.json")
```

### 🪤 Почему пришлось править `storage.py` и `history.py`

Изначально путь был параметром со значением по умолчанию:

```python
def load_churn_model(path: Path = MODEL_PATH) -> dict | None:
```

**Значения по умолчанию в Python вычисляются один раз — при определении
функции.** К моменту теста `path` уже «заморожен» на реальном пути, и
подмена `storage.MODEL_PATH` ничего не меняет.

Решение оказалось упрощением: параметр нигде не использовался, поэтому его
убрали, а функции читают модульную константу в момент вызова:

```python
def load_churn_model() -> dict | None:
    if not MODEL_PATH.exists():
        return None
    return joblib.load(MODEL_PATH)
```

Это частый эффект от тестов: они подсвечивают код, жёстко привязанный к
окружению, и обычно чинятся его **упрощением**, а не усложнением.

### Проблема 2: общее состояние между тестами

`main.model_state` — глобальная переменная модуля. Тест, обучивший модель,
оставил бы её следующему, и проверка «предсказание без обученной модели»
проходила бы или падала в зависимости от порядка запуска. Лечится
перезагрузкой модуля:

```python
importlib.reload(main)   # main выполняется заново → model_state снова None
```

Порядок в фикстуре важен: **сначала** подменить пути, **потом**
перезагрузить `main` — иначе он прочитает настоящие.

Проверить, что изоляция работает, можно прямо из командной строки:

```bash
pytest tests/test_api.py::test_metrics_history tests/test_api.py::test_predict_without_model
```

Обучающий тест идёт первым — если второй всё равно зелёный, состояние не
протекает.

## 🎯 Что именно проверять в тестах

Тест, прибитый к точному числу, ломается при обновлении sklearn и ничего
не говорит о настоящей поломке. Поэтому проверяем **структуру и свойства**:

| Плохо | Хорошо |
|---|---|
| `assert metrics["accuracy"] == 0.7875` | `assert 0.0 <= metrics["accuracy"] <= 1.0` |
| `assert response.json() == {...}` целиком | `assert response.json()["error"]["code"] == "model_not_trained"` |
| `assert probabilities == {"0": 0.9644, ...}` | `assert round(sum(probabilities.values()), 4) == 1.0` |

Отдельно стоит `assert metrics["roc_auc"] > 0.75`: это не «магическое
число из прогона», а осмысленное требование к модели на данных, где сигнал
заложен нами.

## 🔨 Как убедиться, что тесты не бутафория

Полезный приём — **мутационная проверка**: сломать код намеренно и
посмотреть, покраснеют ли тесты. Скопировали папку дня, внесли три поломки,
прогнали:

| Поломка | Результат |
|---|---|
| перепутан порядок колонок признаков | ❌ упал `test_features_to_dataframe_column_order` |
| убрана проверка «модель не обучена» | ❌ упал `test_predict_without_model` |
| `roc_auc` по меткам вместо вероятностей | ✅ **прошёл** — дыра в покрытии |

Третья строка и заставила добавить проверку `roc_auc > 0.75`. Зелёный
набор тестов сам по себе ничего не доказывает — важно знать, что он умеет
краснеть.
