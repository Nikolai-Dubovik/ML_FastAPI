# 🧰 Технологии проекта — как они устроены

Файл объясняет **фреймворки и инструменты**, на которых строится сервис.
Питон как язык опускаем — фокус на том, что добавляется поверх него и как
оно работает «под капотом».

---

## 🗺️ Общая картина: стек

Технологии складываются в слои. Снизу — «железо» обработки запросов,
сверху — удобный код, который пишешь ты:

```
   ┌─────────────────────────────────────────┐
   │  Твой код (main.py): @app.get("/") ...   │   ← что ты пишешь
   ├─────────────────────────────────────────┤
   │  FastAPI         — фреймворк, роутинг,   │
   │                    валидация, доки       │
   ├──────────────────┬──────────────────────┤
   │  Starlette       │  Pydantic            │   ← на этом построен FastAPI
   │  (веб-механика)  │  (валидация данных)  │
   ├──────────────────┴──────────────────────┤
   │  ASGI            — протокол-«разъём»     │   ← общий язык сервера и приложения
   ├─────────────────────────────────────────┤
   │  Uvicorn         — ASGI-сервер           │   ← принимает HTTP из сети
   ├─────────────────────────────────────────┤
   │  Сеть / HTTP / браузер, curl, клиент     │
   └─────────────────────────────────────────┘
```

Ключевая мысль: **FastAPI ничего не принимает из сети сам**. Он только
описывает, *что делать* с запросом. А *принимает* запрос из сети
отдельная программа — сервер (Uvicorn). Связывает их стандарт ASGI.

---

## 🔌 ASGI — протокол, а не библиотека

**ASGI** (Asynchronous Server Gateway Interface) — это не программа,
а **соглашение/спецификация**: договорённость о том, как сервер
и Python-приложение разговаривают друг с другом.

- Раньше в Python был **WSGI** — синхронный: один запрос = занят один
  поток, пока не ответим. Плохо для долгих операций и веб-сокетов.
- **ASGI** — асинхронный наследник. Позволяет обрабатывать много
  соединений «одновременно» через `async/await`, поддерживает WebSocket,
  фоновые задачи и т.д.

Технически ASGI-приложение — это вызываемый объект с сигнатурой
`async def app(scope, receive, send)`, где:
- `scope` — словарь с данными о соединении (тип, путь, заголовки);
- `receive` — корутина, чтобы *получать* события (тело запроса);
- `send` — корутина, чтобы *отправлять* события (ответ).

Тебе это писать вручную не нужно — FastAPI генерирует такой объект сам
(это и есть `app` в `main.py`). Но именно поэтому Uvicorn умеет с ним
работать: они оба «говорят на ASGI».

> Аналогия: ASGI — это как USB-разъём. Uvicorn и FastAPI — два разных
> устройства, но раз у обоих USB, они соединяются без переходников.

## 🚀 Uvicorn — ASGI-сервер

**Uvicorn** — это собственно **сервер**: программа, которая
открывает TCP-порт (по умолчанию `8000`), слушает сеть, разбирает
сырой HTTP и превращает его в ASGI-события для приложения.

Что он делает по шагам:
1. Принимает HTTP-запрос из сокета.
2. Парсит его (метод, путь, заголовки, тело) в `scope`.
3. Вызывает твоё ASGI-приложение (`app`), передавая `scope/receive/send`.
4. Получает от приложения ответ и пишет его обратно в сокет.

Запуск: `uvicorn main:app --reload`
- `main` — модуль (файл `main.py`);
- `app` — объект FastAPI внутри него;
- `--reload` — следит за файлами и перезапускает сервер при изменениях
  (только для разработки; в проде так не делают — дорого и небезопасно).

Под капотом Uvicorn использует `uvloop` и `httptools` (быстрые
C-библиотеки) — отсюда его скорость. Ставится как `uvicorn[standard]`.

> FastAPI = «что отвечать», Uvicorn = «как принять запрос и отдать ответ».

## ⭐ FastAPI — веб-фреймворк

**FastAPI** — фреймворк для создания API. Его суперсила в том, что он
использует **аннотации типов Python** не для красоты, а как источник
правды: из них он строит валидацию, парсинг и документацию.

Главные механизмы:

- **Роутинг через декораторы.** `@app.get("/")` регистрирует функцию как
  обработчик пути `/` и метода `GET`. FastAPI хранит таблицу маршрутов и
  при запросе выбирает нужную функцию.

- **Возврат словаря → JSON.** Если функция вернула `dict`/`list`/Pydantic-
  модель, FastAPI сам сериализует это в JSON и проставит заголовки. Тебе
  не нужно вручную звать `json.dumps`.

- **`async` и обычные функции.** Обработчик можно писать и как
  `def`, и как `async def`. Асинхронные выполняются в общем событийном
  цикле; синхронные FastAPI аккуратно уводит в пул потоков, чтобы они не
  блокировали остальные запросы.

- **Внедрение зависимостей (Depends).** Механизм, чтобы переиспользовать
  логику (авторизация, доступ к модели ML, к БД) — пригодится в следующие
  дни.

- **Автодокументация** (см. ниже) — генерируется бесплатно.

Важно: FastAPI — это «клей» поверх двух библиотек. Сам он почти не
обрабатывает сеть и не валидирует данные — он делегирует:
**Starlette** отвечает за веб-механику, **Pydantic** — за данные.

---

## 🧩 Starlette — веб-ядро под FastAPI

**Starlette** — лёгкий ASGI-тулкит, на котором FastAPI построен.
Именно Starlette реализует «скучную», но важную веб-механику:

- маршрутизацию (сопоставление пути и обработчика);
- объекты `Request` / `Response`;
- middleware (промежуточные обработчики: CORS, логирование, сжатие);
- фоновые задачи, WebSocket, тестовый клиент.

Ты редко работаешь со Starlette напрямую — FastAPI оборачивает её в
более удобный интерфейс. Но знать полезно: когда видишь в документации
`from starlette...` — это и есть фундамент FastAPI.

## ✅ Pydantic — валидация и модели данных

**Pydantic** — библиотека для описания структуры данных через классы и
их **автоматической валидации**. Это второй столп FastAPI.

Как работает: ты объявляешь класс с типизированными полями, а Pydantic
на основе типов сам проверяет и приводит входные данные:

```python
from pydantic import BaseModel

class FeatureVectorChurn(BaseModel):
    monthly_fee: float
    support_requests: int
    region: str
```

Если в запросе придёт `support_requests: "пять"` — Pydantic вернёт
понятную ошибку 422 с указанием поля, *до* того как код доберётся до
твоей логики. Под капотом ядро Pydantic v2 написано на Rust — поэтому
валидация быстрая.

В день 1 Pydantic ещё не нужен (эндпоинт возвращает простой словарь), но
со дня 2 именно через него опишем входные признаки оттока (`churn`).

## 📖 OpenAPI и Swagger UI — документация «из коробки»

FastAPI на основе твоих типов и маршрутов автоматически генерирует
**OpenAPI-схему** — это машинно-читаемое описание всего API в формате
JSON (доступно по `/openapi.json`).

Поверх этой схемы FastAPI отдаёт две готовые веб-странички:
- **Swagger UI** — `http://127.0.0.1:8000/docs` — интерактивная
  документация, где можно прямо из браузера послать запрос к эндпоинту;
- **ReDoc** — `http://127.0.0.1:8000/redoc` — альтернативный, более
  «читательский» вид.

Ничего настраивать не надо — описал эндпоинт, доки появились сами.
Это очень удобно для проверки задания глазами.

## 🔄 Что происходит при одном запросе (день 1)

Соберём всё вместе на примере `GET /`:

1. Браузер шлёт `GET /` на `127.0.0.1:8000`.
2. **Uvicorn** принимает соединение, парсит HTTP, формирует ASGI-`scope`.
3. Uvicorn вызывает ASGI-приложение **FastAPI** (`app`).
4. FastAPI (через **Starlette**) по таблице маршрутов находит функцию,
   привязанную к `GET /`, и вызывает её.
5. Функция возвращает `{"message": "ml churn service is running"}`.
6. FastAPI сериализует словарь в JSON, ставит `Content-Type: application/json`.
7. Ответ через ASGI уходит в Uvicorn, тот пишет HTTP 200 в сокет.
8. Браузер показывает JSON.

## 📦 Итоговый список технологий дня 1

| Технология | Роль | Где в коде/командах |
|------------|------|---------------------|
| **Uvicorn** | ASGI-сервер, принимает HTTP | `uvicorn main:app --reload` |
| **ASGI**    | протокол связи сервер↔приложение | неявно, внутри |
| **FastAPI** | фреймворк: роуты, JSON, доки | `app = FastAPI()`, `@app.get("/")` |
| **Starlette** | веб-механика под FastAPI | внутри FastAPI |
| **Pydantic** | валидация данных | со дня 2 (модели `*Churn`) |
| **OpenAPI / Swagger UI** | автодокументация | страница `/docs` |
