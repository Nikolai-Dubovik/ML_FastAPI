# 🧰 Новые технологии дня 2 — Pydantic и тело запроса

В дне 1 работали Uvicorn + FastAPI, а Pydantic упоминался вскользь. Сегодня
**Pydantic выходит на первый план** — на нём держится вся работа с входными
данными. Разберём, что это и как оно сцеплено с FastAPI.

---

## ✅ Что такое Pydantic

**Pydantic** — библиотека для описания структуры данных через обычные классы
Python и их **автоматической валидации**. Идея: ты объявляешь, *какие поля и
каких типов* ожидаешь, а Pydantic сам проверяет вход, приводит типы и при
ошибке выдаёт понятное сообщение.

Это та же мысль, что и аннотации типов в Python (`x: int`), но с одним
большим отличием: обычные аннотации **ничего не проверяют** в рантайме — это
просто подсказки. Pydantic же делает их **исполняемыми**: на их основе
реально валидирует данные во время работы программы.

> Под капотом ядро Pydantic v2 написано на Rust (пакет `pydantic-core`),
> поэтому валидация быстрая даже на больших объёмах.

## 🏗️ BaseModel — базовый кирпич

Модель — это класс, унаследованный от `pydantic.BaseModel`. Поля
объявляются как типизированные атрибуты класса:

```python
from pydantic import BaseModel

class FeatureVectorChurn(BaseModel):
    monthly_fee: float
    support_requests: int
    region: str
```

Что даёт наследование от `BaseModel`:

- **Конструктор «бесплатно»**: `FeatureVectorChurn(monthly_fee=9.9, ...)`.
- **Валидация при создании**: передал в `int` строку `"пять"` — получишь
  ошибку `ValidationError`, объект не создастся.
- **Мягкое приведение типов** (coercion): строка `"10"` в поле `int`
  превратится в число `10`. Полезно, т.к. данные из сети часто строковые.
- **Сериализация**: `model_dump()` → словарь, `model_dump_json()` → JSON.
- **JSON Schema**: `model_json_schema()` — описание модели, которое FastAPI
  использует для документации (см. ниже).

## 🔢 Типы полей и что значит «валидация»

Типы из задания читаются буквально:

| Поле | Тип | Что проверяет Pydantic |
|------|-----|------------------------|
| `monthly_fee` | `float` | число (int приведётся к float) |
| `support_requests` | `int` | целое; `3.5` → ошибка, `"3"` → `3` |
| `region` | `str` | строка |
| `autopay_enabled` | `int` | целое (по заданию 0/1, **не** `bool`) |

«Валидация» = проверка, что пришедшие данные соответствуют объявленной
схеме, **до** того как они попадут в твою логику. Если что-то не так,
дальше код не выполняется — возвращается ошибка с точным указанием поля.

## 🧬 Наследование моделей (DRY)

`DatasetRowChurn` — это «строка датасета»: все те же признаки **плюс**
целевое поле `churn`. Чтобы не переписывать 9 полей заново, наследуем модель
от модели:

```python
class DatasetRowChurn(FeatureVectorChurn):
    churn: int
```

`DatasetRowChurn` получает все поля родителя и добавляет своё. Это обычное
наследование классов Python, но Pydantic корректно «собирает» итоговую схему
из родителя и потомка. Меньше дублирования — меньше шансов на расхождения.

## 🔗 Как FastAPI использует Pydantic для тела запроса

Главная связка дня. Когда в обработчике аргумент аннотирован Pydantic-моделью:

```python
@app.post("/predict")
def predict(features: FeatureVectorChurn):
    return features
```

FastAPI по типу аргумента понимает: **тело запроса (JSON) надо разобрать в
`FeatureVectorChurn`**. Дальше он автоматически:

1. читает «сырое» тело запроса (байты);
2. парсит его как JSON;
3. отдаёт Pydantic на валидацию по схеме `FeatureVectorChurn`;
4. если всё ок — кладёт готовый объект в `features`;
5. если нет — **сам** возвращает ответ `422 Unprocessable Entity` со
   списком проблемных полей. Твой код при этом даже не вызывается.

То есть проверку входных данных пишешь не ты — её генерирует FastAPI из
объявленной модели. Ты сразу работаешь с валидным объектом.

> Разница с днём 1: там `GET /` ничего не принимал и отдавал готовый
> словарь. Здесь `POST /predict` **принимает** структурированные данные —
> и именно для этого нужен Pydantic.

---

## 📤 Сериализация ответа

Обработчик возвращает объект `features` (Pydantic-модель). FastAPI сам
превратит его в JSON (через `model_dump`) и проставит
`Content-Type: application/json`. Поэтому «эхо» возвращает ровно те поля,
что пришли. (При желании на эндпоинт можно повесить `response_model=...` —
тогда FastAPI ещё и провалидирует/отфильтрует ответ; сегодня это не нужно.)

---

## 📖 Где это видно в /docs (OpenAPI)

FastAPI берёт JSON Schema каждой модели и встраивает в OpenAPI-описание.
Поэтому на странице `http://127.0.0.1:8000/docs` автоматически появятся:

- эндпоинт `POST /predict` с примером тела запроса;
- кнопка **Try it out** — можно отправить запрос прямо из браузера;
- раздел **Schemas** с моделью `FeatureVectorChurn`.

> Важно: в `/docs` попадают только модели, на которые ссылается хотя бы один
> эндпоинт. `DatasetRowChurn` определён в коде (для строк датасета), но пока
> нигде не используется — поэтому в Schemas он появится позже (день 3+),
> когда его задействует эндпоинт. На корректность кода это не влияет.

Ничего отдельно описывать для документации не нужно — она выводится из
тех же моделей, что и валидация. Один источник правды.

---

## 🔄 Путь запроса `POST /predict` целиком

1. Клиент шлёт `POST /predict` с JSON-телом признаков.
2. **Uvicorn** принимает HTTP, передаёт в **FastAPI** (как в дне 1).
3. FastAPI видит аргумент типа `FeatureVectorChurn` → парсит JSON и зовёт
   **Pydantic** на валидацию.
4. Валидно → объект попадает в `features`; невалидно → FastAPI отдаёт 422.
5. Обработчик возвращает `features`; FastAPI сериализует в JSON.
6. Ответ 200 уходит обратно через Uvicorn клиенту.
