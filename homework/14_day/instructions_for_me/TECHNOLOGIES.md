## 📦 Python-пакеты и почему плоско — плохо

К дню 13 в папке лежало ~десяток `.py` вперемешку: и Pydantic-модели, и ML, и
роуты. Пока файлов мало — терпимо, но растёт — теряешься. Решение —
**пакеты**: папки с `__init__.py`, сгруппированные по смыслу.
```
app/
├── __init__.py     # делает app пакетом
├── api.py          # веб-слой
├── schemas.py      # контракты данных
├── config.py       # настройки
└── ml/             # всё про машинное обучение
    └── __init__.py
```
Импорт становится «адресным»: `from app.ml.model import train_churn_model` —
сразу видно, что это ML-слой. `__init__.py` (пусть даже пустой) обязателен:
без него Python не считает папку пакетом.

## 🗂️ Разделение по слоям (api / ml / schemas / config)

Стандартная раскладка backend-проекта — по **ответственности**:

| Слой | Папка/файл | Отвечает за |
|---|---|---|
| **api** | `app/api.py` | HTTP-эндпоинты, разбор запроса/ответа |
| **ml** | `app/ml/*` | данные, пайплайн, обучение, предсказание |
| **schemas** | `app/schemas.py` | Pydantic-контракты (вход/выход) |
| **config** | `app/config.py` | пути и настройки в одном месте |
| **main** | `app/main.py` | сборка приложения из слоёв |

Бонус уборки: `models.py` (Pydantic) переименован в `schemas.py` — уходит
путаница с папкой артефактов `models/`. Имя файла теперь говорит правду:
это **схемы данных**, а не ML-модель.

## 🧭 APIRouter — эндпоинты отдельно от приложения

Раньше все `@app.get/post` висели прямо на `app` в `main.py`. `APIRouter`
позволяет описать роуты **отдельно**, а потом подключить:
```python
# app/api.py
from fastapi import APIRouter
router = APIRouter()

@router.post("/predict")
def predict(...): ...

# app/main.py
app = FastAPI(title="ML Churn Service")
app.include_router(router)
```
`router` работает как мини-приложение: те же декораторы, но он не привязан к
конкретному `app`. Так `main.py` становится тонким «сборщиком», а эндпоинты
живут в своём модуле. На больших проектах роутеров несколько (по темам) — мы
готовим для этого почву.

## ⚙️ Централизованный конфиг

Пути к данным и артефактам были разбросаны по модулям
(`Path(__file__).resolve()...`). Собираем их в один `config.py`:
```python
DATA_PATH = Path(os.getenv("CHURN_DATA_PATH", PROJECT_ROOT / "data" / "churn_dataset.csv"))
ARTIFACTS_DIR = Path(os.getenv("CHURN_ARTIFACTS_DIR", BASE_DIR.parent / "artifacts"))
MODEL_PATH = ARTIFACTS_DIR / "churn_model.joblib"
HISTORY_PATH = ARTIFACTS_DIR / "training_history.json"
```
Один взгляд — и понятно, что и откуда читается; поменять путь можно в одном
месте (или через env, как в Docker дня 13). Это принцип **single source of
truth**, но уже для конфигурации, а не для признаков.

## 🧹 Рефакторинг ≠ переписывание

Ключевое правило дня: **поведение не меняем**, меняем только форму. Отсюда
порядок действий:
1. переносим файлы и правим импорты;
2. после каждого шага гоняем `pytest -q` — тесты дня 12 ловят регрессию;
3. удаляем мёртвый код и «учебные» комментарии, где имя функции уже всё
   объясняет.

Именно поэтому тесты написали **раньше** рефакторинга: они — страховочная
сетка, позволяющая смело двигать код.

## 📖 README как часть продукта

Код без документации — недоделанный продукт. **README проекта** (отдельный от
этих учебных заметок) отвечает на вопросы нового человека:
- **зачем** сервис (предсказание оттока);
- **какой формат данных** (колонки `churn_dataset.csv`, что числовое/категориальное);
- **как запустить** — локально и в Docker;
- **как дёрнуть** — примеры запросов к `/model/train` и `/predict`;
- **как проверить** — `pytest`.

Хорошее правило: по README проект должен подниматься с нуля **без чтения
исходников**.

## 🔖 Фиксация в git

Финальный шаг — сохранить итог в системе контроля версий:
```bash
git add homework/14_day
git commit -m "day 14: финальный рефакторинг структуры и README churn-сервиса"
```
Осмысленный коммит — это «точка сохранения» и запись в истории проекта: видно,
*что* и *зачем* менялось. (`artifacts/`, `.venv`, `__pycache__` в коммит не
идут — они в `.gitignore`.)
