# 🧰 Новые технологии дня 14 — пакеты, APIRouter и рефакторинг

День 14 не добавляет сервису ни одной функции. Он меняет **форму** кода:
из семи файлов в одной папке получается пакет с ясными границами. Это
последний навык курса — умение навести порядок, ничего не сломав.

---

## 📦 Пакеты Python: папка, которая стала модулем

Папка с `__init__.py` — это **пакет**: её содержимое импортируется через
точку.

```python
from app.ml.preprocessing import FEATURE_COLUMNS
from app import config, state
```

Что это даёт помимо красоты:

- **Явные границы.** `app/ml/` — всё, что знает про машинное обучение;
  `app/api.py` — всё, что знает про HTTP. Модель ничего не знает про
  FastAPI, эндпоинты — про sklearn.
- **Уникальные имена.** Раньше `models.py` (Pydantic-модели) соседствовал с
  папкой `models/` (артефакты) — источник путаницы. Стало `app/schemas.py`
  и `artifacts/`.
- **Порядок выполнения.** `app/__init__.py` выполняется **до** любого
  модуля пакета — этим мы и пользуемся для настройки логов.

Структура из задания — типовая для FastAPI-проектов:

| Модуль | Отвечает за |
|---|---|
| `config` | пути, константы окружения |
| `schemas` | контракты данных (что принимаем и отдаём) |
| `ml` | предметная логика: данные, модель, хранение |
| `api` | HTTP-слой: маршруты и коды ответов |
| `main` | сборка приложения |

## 🛣️ APIRouter — маршруты отдельно от приложения

```python
# app/api.py
router = APIRouter()

@router.get("/health")
def health():
    ...
```

```python
# app/main.py
app = FastAPI(title="ML Churn Service")
register_error_handlers(app)
app.include_router(router)
```

`APIRouter` — тот же набор декораторов (`@router.get`, `@router.post`), но
не привязанный к конкретному приложению. Маршруты объявляются в одном
месте, подключаются в другом.

Зачем это здесь: `main.py` перестал быть свалкой. Теперь он читается за
пять секунд и отвечает на единственный вопрос — «из чего собран сервис».
В больших проектах роутеров несколько (`users`, `orders`, `admin`), и у
каждого свои префикс и теги: `app.include_router(router, prefix="/api/v1")`.

## 🗃️ Состояние в отдельном модуле

Было — глобальная переменная в `main.py` и `global` в обработчике:

```python
model_state = load_churn_model()

@app.post("/model/train")
def model_train(...):
    global model_state          # ← ключевое слово, которое всех смущает
    model_state = save_churn_model(...)
```

Стало — модуль `app/state.py` и обычное присваивание атрибута:

```python
from app import state

state.model_state = save_churn_model(...)
```

`global` не нужен: мы меняем не локальную переменную, а атрибут объекта
модуля. Читается честнее — сразу видно, что состояние живёт в `state`, а
не «где-то в этом файле».

Бонус для тестов: чтобы вернуть сервис в исходное положение, достаточно
перезагрузить **один** модуль:

```python
importlib.reload(state)
```

Здесь важно свойство `reload`: он **переиспользует существующий объект
модуля**, а не создаёт новый. Поэтому все, кто когда-то сделал
`from app import state`, продолжают видеть тот же объект — уже с
обновлённым содержимым. Если бы состояние осталось в `api.py`, пришлось бы
перезагружать и `api`, и `main` (маршруты копируются в приложение при
`include_router`) — каскад, который легко сломать.

## 🪤 Та же ловушка на новом уровне: импорт константы

В дне 12 мы уже спотыкались о значения по умолчанию. В пакете та же
ошибка выглядит иначе:

```python
from app.config import MODEL_PATH     # ❌ имя скопировано в момент импорта
from app import config                # ✅ читаем config.MODEL_PATH при вызове
```

`from … import X` копирует **значение** в пространство имён модуля. Подмена
`config.MODEL_PATH` в тесте после этого ни на что не влияет — модуль держит
свою копию. Импорт самого модуля оставляет один общий источник правды.

Тот же корень был у параметра `csv_path: Path = config.DATA_PATH` в
`ChurnDataset`: значение по умолчанию вычисляется при импорте. Параметр
никто не передавал — удалили и его, оставив чтение `config.DATA_PATH`
внутри метода.

**Правило дня:** конфигурацию читаем в момент использования, а не в момент
импорта.

## 🧹 Что такое «удалить неиспользуемый код»

Задание требует чистки, и здесь легко впасть в крайности: либо не найти
ничего, либо начать «улучшать» рабочий код. Полезно держать критерий:
удаляем то, что **доказуемо** не используется.

| Находка | Как доказано |
|---|---|
| `ChurnDataset.to_rows()` | `grep -rn "to_rows"` — единственное вхождение это само определение |
| параметр `csv_path` | все вызовы — `ChurnDataset()` без аргументов |
| `df is None or df.empty` | `pd.read_csv` либо возвращает DataFrame, либо бросает исключение — `None` невозможен |
| `df=None` в `feature_schema` | единственный вызывающий всегда передаёт датасет |
| `.get("model_type")` | страховка под формат bundle, который больше не встречается |

Мёртвый код опаснее, чем кажется: он выглядит поддерживаемым, участвует в
поиске по проекту и создаёт иллюзию, что случай обрабатывается. Недостижимая
ветка `df is None` — ровно такой случай: читатель думает, что датасет может
не загрузиться, хотя на самом деле сервис до этой строки просто не доживёт.

А вот чего **не** стоит делать под флагом чистки: удалять комментарии,
объясняющие ловушки (`handle_unknown="ignore"`, `protected_namespaces=()`,
«фильтр раньше среза»). Они не мусор, а объяснение неочевидного.

## 🛡️ Рефакторинг под защитой тестов

Главный вопрос любого переноса файлов — «а точно ничего не сломалось?».
Отвечать на него памятью и внимательностью не нужно: 12 тестов дня 12–13
переехали вместе с кодом и после рефакторинга остались зелёными. Это и есть
их основная ценность — не поймать баг, который вы уже знаете, а **разрешить
менять код без страха**.

Порядок, который стоит запомнить:

1. переносим файлы, чиним импорты;
2. `pytest -q` — красный? чиним, пока не зелёный;
3. только потом чистим мёртвый код;
4. `pytest -q` снова;
5. живая проверка (uvicorn + curl) и сборка контейнера — тесты не покрывают
   Docker и пути внутри образа.

Пункт 5 не формальность: правка `dataset.py` затронула разрешение пути к
CSV, а такие вещи ломаются именно в контейнере, где структура папок другая.
Поэтому образ пересобирался и проверялся после чистки.

## 📖 README как часть продукта

Последний пункт задания — README проекта, и это не бюрократия. Хороший
README отвечает на четыре вопроса нового человека:

1. **Зачем это?** — предсказание оттока клиентов;
2. **Какие данные нужны?** — таблица колонок с типами и допустимыми
   значениями;
3. **Как запустить?** — локально и в Docker, копируемыми командами;
4. **Как этим пользоваться?** — примеры запросов с реальными ответами.

Практическое правило: команды и JSON в README должны быть **скопированы из
рабочего терминала**, а не написаны по памяти. README с непроверенными
примерами хуже отсутствующего — он тратит время читателя на отладку
документации.
