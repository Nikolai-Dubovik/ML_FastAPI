## 📜 Контракт признаков: почему это важно

Модель — придирчивый потребитель: ей нужен **ровно тот же** набор
признаков, что при обучении. Несовпадение имени, типа или неизвестная
категория — и предсказание либо упадёт, либо (хуже) тихо посчитается
неправильно.

До дня 9 этот контракт существовал неявно — «смотри код». Теперь у него
два явных воплощения:
- **внутри** — функция `features_to_dataframe()`: единственный путь из
  Pydantic-объектов во вход модели;
- **снаружи** — эндпоинт `GET /model/schema`: машиночитаемое описание
  «что присылать».

---

## 🚪 Единая точка подготовки — features_to_dataframe

```python
def features_to_dataframe(features: list[FeatureVectorChurn]) -> pd.DataFrame:
    return pd.DataFrame([f.model_dump() for f in features], columns=FEATURE_COLUMNS)
```

В день 7 этот код жил внутри `predict_churn()` — работало, но правило
«порядок признаков совпадает с обучением» держалось на одном месте в
коде. Вынос в `preprocessing.py` рядом с `FEATURE_COLUMNS` делает правило
структурным: захочешь подготовить признаки иначе — просто негде.

Принцип называется **single source of truth**: списки признаков объявлены
один раз (день 4), и все — обучение, предсказание, схема — читают их из
одного места. Разъехаться им негде.

## 🔍 Интроспекция Pydantic — model_fields

Для схемы нужны типы признаков. Не пишем их руками второй раз — **у нас
уже есть** источник правды: `FeatureVectorChurn` из дня 2. Pydantic умеет
рассказывать о своих полях:

```python
FeatureVectorChurn.model_fields
# {"monthly_fee": FieldInfo(annotation=float, ...),
#  "region": FieldInfo(annotation=str, ...), ...}

FeatureVectorChurn.model_fields["monthly_fee"].annotation.__name__
# 'float'
```

Это **интроспекция** — код читает описание самого себя. Поменяется тип в
модели → `/model/schema` обновится автоматически, без ручной синхронизации
двух списков.

> Тонкость: `annotation.__name__` красиво работает для простых типов
> (`float`, `int`, `str`). Для `Optional[X]` или union-типов пришлось бы
> разбирать аннотацию — нам пока не нужно.

## 🗺️ GET /model/schema — самоописывающийся сервис

```json
{"name": "region", "type": "str", "role": "categorical",
 "categories": ["africa", "america", "asia", "europe"]}
```

Каждый признак описан трижды:
- **type** — тип значения (из Pydantic-модели);
- **role** — numeric или categorical (из списков дня 4): клиент понимает,
  что масштабируется, а что кодируется;
- **categories** — для категориальных: допустимые значения из датасета
  (`sorted(df[col].unique())`).

Идея из мира production ML: сервис **сам документирует свой входной
формат**. Клиенту не нужно читать исходники — он спрашивает `/model/schema`
и программно строит валидный запрос. Это дополняет `/docs`: Swagger — для
человека, schema — для кода.

## 🧳 «Один объект» — ревизия дней 5–6

Пункт задания «предобработка и модель сохраняются как один объект» был
выполнен заранее — правильной архитектурой:

```
joblib-файл
└── bundle
    ├── pipeline            ← ColumnTransformer (scaler + one-hot) + модель
    ├── model_type, hyperparameters
    ├── trained_at
    └── metrics
```

Внутри pipeline **обученные** трансформеры: скейлер помнит mean/std с
train, энкодер — список категорий. Если бы сохранялась только модель,
после рестарта предсказания стали бы мусором (нечем масштабировать).
Проверка дня: рестарт → `/predict` работает — значит, предобработка
действительно приехала с моделью.
